# Dori 주행 명령 해석기와 TTA

Nav2의 `cmd_vel`은 원하는 몸체 속도다. 실제 Dori는 출발 저항, 모터 가감속 제한, 구동 지연 때문에 이 값을 단순히 비율로 나누어 보내면 잘 움직이지 않았다. 수동 조이스틱 주행을 기록해 **원하는 속도를 실제 움직임이 나오는 조이스틱 입력 크기로 번역**하는 해석기를 추가했다.

## 명령 흐름

```text
목표 좌표 → Nav2 경로 계획·충돌 검사
         → /nav/cmd_vel_raw → velocity_smoother → /nav/cmd_vel
         → nav_drive_bridge + MotionInterpreter
         → /auto/cmd_vel (정규화된 조이스틱 입력)
         → 기존 drive_controller → 가감속·토크 제한 → 모터
```

경로 계획은 Nav2가, 입력 변환은 해석기가, 실제 모터 구동과 보호 제한은 기존 제어기가 맡는다. 해석기는 지도·오도메트리·TF를 만들지 않는다. 탈선 방지와 비상정지, CAN/센서 timeout, 가감속·토크 제한은 유지한다.

## 수동 주행에서 얻은 기본 모델

2026-10-23 수동 주행 174.6초, 3,465개 표본을 사용했다. 보호 제한 **이후의 실제 바퀴 목표**와 LiDAR 취득 시각을 맞춰 분석했다.

| 항목 | 초기 설정 |
|---|---:|
| 전진 출발 입력 | 0.22 |
| 전진 응답 계수 | 0.62 m/s / 입력 |
| 주행 중 회전 응답 계수 | 1.67 rad/s / 입력 |
| 전진 응답 지연 | 0.15초 |
| 회전 응답 지연 | 0초 설정, 별도 지연 미식별 |
| 입력 범위 | 기존 조이스틱과 같은 −1…1 |
| Nav2 몸체 속도 요구 상한 | 0.3 m/s, 1.2 rad/s |

전진 영역의 모델은 `v = 0.62 × max(u_v − 0.22, 0)`이며, 코드의 부호 대칭 초기 모델은 `v = sign(u_v) × 0.62 × max(|u_v| − 0.22, 0)`이다. 회전은 전진 중 `w = 1.67 × u_w`로 모델링한다. 따라서 0.3m/s 요구에는 `u ≈ 0.22 + 0.3/0.62 ≈ 0.70`을 시작값으로 사용한다. 기존 정규화 스케일 `1.72m/s`, `7rad/s`로 단순히 나눈 값과 다르다. 이 계수는 관측한 몸체 응답이며 바퀴 반경·기어비를 바꾸는 값이 아니다.

실행은 `stop → start → track → brake` 상태로 구분한다. 역모델의 기본 입력에 LiDAR 속도 오차의 PI 보정을 더하고, 실제 속도가 요구를 크게 넘으면 입력을 줄인다. 현재 실물 설정에서는 출발 입력의 자동 학습을 끄고 0.22로 고정한다.

## 지연과 보호 제한의 취급

- `/drive/wheel_control`에서 가감속 제한을 거친 바퀴 목표를 읽어 실제 적용 입력을 복원한다.
- 명령 이력을 저장하고 `LiDAR 시각 − 응답 지연`에 대응하는 입력을 골라 학습에 사용한다. 시각이 맞는 자료가 없으면 학습하지 않는다.
- 제한기가 아직 새 요청을 따라가는 동안에는 양의 적분 보상을 쌓지 않는다. 제한기 지연을 출발 저항으로 잘못 학습하는 것을 줄인다.
- 0 요청과 목표 취소는 공통 halt로 연결해 이전 제한기 출력이 남아 계속 움직이지 않게 한다.
- 엔코더는 약 0.3초 구간의 위치 차분으로 계산한다. 몸체가 실제 이동했는지는 LiDAR odometry를 기준으로 본다.

## TTA: 주행 중 응답 계수 보정

여기서 TTA는 **실행 중 데이터로 제한된 응답 모델을 조금씩 보정하는 온라인 식별**이다. 신경망 가중치를 역전파하거나 경로 정책을 학습하는 구조는 아니다. 바뀌는 값은 전진·회전 축의 `response_gain`이다.

1. 현재 요청·실제 적용 입력·LiDAR 몸체 속도·엔코더 방향을 수집한다.
2. LiDAR 취득 시각과 축별 응답 지연에 맞는 과거 적용 입력을 찾는다.
3. 아래 조건이 맞는 새 측정에만 `관측 gain = 몸체 속도 / (적용 입력 크기 − 출발 입력)`을 계산한다.
4. 관측 gain을 초기 gain의 0.25…2배로 제한하고, 현재 gain은 **초당 최대 3%**만 변경한다.
5. 다음 제어 주기부터 새 gain으로 요청 속도를 입력 크기로 변환한다.

학습 조건:

- 새로운 LiDAR 타임스탬프이며 요구가 1초 이상 안정적일 것.
- LiDAR와 엔코더 모두 요청 방향으로 움직일 것. 바퀴만 돌고 몸체가 정지한 표본은 제외한다.
- 적용 입력이 출발 입력보다 충분히 크고, 적용 입력과 해석기 요청 차이가 작을 것.
- 몸체 속도 오차와 LiDAR/엔코더 속도 비율이 허용 범위일 것.
- 센서·TF·CAN 등 기존 주행 gate가 유효할 것.

이 조건은 미끄럼을 완전히 판별하는 추정기는 아니다. 수동 기록에서 엔코더 환산 속도는 LiDAR 몸체 속도의 약 1.94배(직진), 2.17배(회전)였다. 엔코더는 방향과 응답 확인에 사용하고, 몸체 속도의 절대 기준으로 그대로 믿지 않는다.

학습값은 **현재 실행 메모리에만 유지**한다. 목표 정지 때 PI 적분은 초기화하지만 학습 gain은 유지하며, 노드를 재시작하면 YAML의 초기 gain으로 돌아간다. 자동 파일 저장은 하지 않는다.

## 곡선 주행과 원형 정렬

이 기구는 제자리 회전보다 움직이면서 회전하는 편이 잘 동작한다. `motion.arc_only: true`에서는 전진·후진 요청이 0이면 회전 입력도 0이다. 안쪽 바퀴가 반대 방향으로 돌지 않도록 조향 크기를 제한한다. 회전을 위해 임의의 전진 명령을 추가하지 않는다.

작은 조향 요구(0.15rad/s 이하)는 적분 보정을 기본 회전 입력의 절반 이내로 제한하고, 응답이 부족할 때도 0.6초 기다린 뒤 누적한다. 기존 모터 가감속 제한은 그대로다.

목표 방향 때문에 만들어지는 큰 원형 경로는 이 해석기의 gain과 별개다. 현재 일반 목적지는 방향을 참고값으로 두고 30cm 이내 도착으로 종료하며, 경로 계획도 접근 방향을 자유롭게 선택한다. 상대 거리 명령은 별도 10cm 도착 판정을 쓴다. 경로·회전 반경·장애물 검사까지 없애는 것은 아니다.

## 파일과 재보정 도구

- 구현: `ros2_ws/src/robot_navigation/scripts/motion_interpreter.py`
- 센서/명령 시각 정렬 및 주행 gate: `ros2_ws/src/robot_navigation/scripts/nav_drive_bridge.py`
- 실물 파라미터: `ros2_ws/src/robot_navigation/config/motion_interpreter.yaml`
- 기준 계수와 검증 통계: [drive_response_fit.json](evidence/real_robot/drive_response_fit.json). 원시 기록은 원본 작업공간에 보존하며 실행에 필요하지 않다.
- 새 수동 기록/분석: `ros2_ws/tools/record_manual_drive.py`, `ros2_ws/tools/fit_drive_response.py`
- 진단 토픽: `/navigation/motion_interpreter`
- 회귀 시험: `ros2_ws/tests/test_motion_interpreter.py`, `ros2_ws/tests/test_nav_drive_timing.py`

진단에는 `desired`(요구 몸체 속도), `applied`(제한기 후 입력), `encoder`, 축별 `phase`, `ground_speed`, `response_gain`, `start_input`, `learned_samples`가 나온다. 반응이 느릴 때에는 먼저 `desired → input → applied → ground_speed` 순서를 비교한다. `applied` 자체가 늦는지, 적용은 됐지만 몸체가 안 움직이는지 구분한 뒤 조정해야 한다.

수동 전진·곡선 주행으로 보정한 모델이다. 후진 복구는 기존 LiDAR 충돌 검사와 함께 이 모델을 초기값으로 사용하지만, 후진 전용 실물 응답 계수는 따로 교정하지 않았다. 소프트웨어 시험 결과와 실제 바닥·하중에서의 정밀도를 구분한다.

## 제한기 이후 입력 복원과 저수준 변환

공통 기구 상수 `R=0.234`, `L=0.184`, 정규화 스케일 `S_v=1.72`, `S_w=7.0`을 사용한다. 해석기 출력 `u_v,u_w`를 하위 제어기에 전달하면 기존 제한기를 거친 뒤 좌우 바퀴 목표(rad/s)가 만들어진다.

```text
v_cmd = S_v × u_v
w_cmd = S_w × u_w
ω_left  = (v_cmd − w_cmd × L/2) / R
ω_right = (v_cmd + w_cmd × L/2) / R
```

온라인 모델은 이 요청을 바로 ‘적용 완료’로 보지 않는다. `/drive/wheel_control.target_velocity`에서 다음을 복원한다.

```text
u_v_applied = R × (ω_left + ω_right) / (2 × S_v)
u_w_applied = R × (ω_right − ω_left) / (L × S_w)
```

`nav_drive_bridge.learning_input()`은 각 축의 `scan_stamp − response_delay`보다 늦지 않은 마지막 적용 명령을 고른다. 그 시각과 0.3초 이상 벌어진 자료는 학습에 쓰지 않는다. 인코더는 최신 약 0.3초 위치 차분을 쓰며 순환각은 8π로 처리한다. 필터링한 LiDAR 몸체 속도가 학습의 실제 응답이다.

출발 상태에서는 기본 역모델 외에 `startup_rate`에 따른 제한된 추가 입력이 가능하지만, 회전 축의 현재 설정은 0이다. 직진·회전 모두 `adapt_start=false`이므로 출발 offset을 주행 중 다시 학습하지 않는다. 낮은 요구 속도는 축별 stopped-demand 문턱에서 0으로 처리하며, 경로를 벗어나게 만드는 임의 전진 속도를 추가하지 않는다.

`rolling_arc()`는 정규화 각도 입력을 `0.9 × 2 × |u_v| × S_v / (L × S_w)` 이내로 제한한다. 이 식은 안쪽 바퀴가 명령 진행 방향을 유지하도록 하는 조건이며, 요청 경로의 곡률을 새로 계획하는 함수가 아니다. 역모델과 보호 이후 응답 때문에 실제 경로/반경은 별도로 실기 검증해야 한다.

## 새 바닥·하중에서 다시 보정하기

구동·LiDAR odometry가 준비된 수동 모드에서 작업공간 `ros2_ws` 기준:

```bash
source scripts/env.sh
python3 tools/record_manual_drive.py --duration 180 --output log/manual_drive.jsonl
# 기록 중 사람이 컨트롤러로 전진·완만한 좌우 곡선을 실행한다.
python3 tools/fit_drive_response.py log/manual_drive.jsonl --output log/drive_fit.json
# 그래프가 필요하면 python3-matplotlib 설치 후 --plot log/drive_fit.png 추가
```

도구는 기록/분석만 하고 로봇 파라미터를 자동 변경하지 않는다. 충분한 전진/회전 구간을 확보하고 잔차·지연·검증 구간을 확인한 후 `motion_interpreter.yaml`의 gain/offset/delay를 명시적으로 갱신한다. 첫 유효 입력부터 마지막 측정까지 시간 구간의 앞 67%로 맞추고 뒤 33%로 검증한다. 0.5초 차분 창이 겹치므로 독립 표본 정확도로 해석하지 않는다.
